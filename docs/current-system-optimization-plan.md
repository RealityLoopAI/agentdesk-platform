# AgentDesk 当前系统优化方案

> 文档状态：待实施  
> 基线日期：2026-08-06（Asia/Shanghai）  
> 适用项目：`agentdesk-platform`

## 1. 执行摘要

当前 AgentDesk 全套服务处于健康状态。历史日志中的 14 次 Host 退出均伴随 `SIGTERM`，属于停止或重启流程，没有证据表明 Host 在持续自发崩溃。

系统当前的卡顿、不稳定感和运维噪声是真实存在的，主要集中在以下方面：

1. 容器空闲退出配置没有传入 Runner，导致容器只能等到 30 分钟绝对上限后被强杀；
2. 图片与 JSON 监控高频递归扫描同一个 SMB，在不可用时仍每 5 秒重试；
3. Host 在回收容器时存在同步 Docker 操作，会阻塞 Node.js 唯一事件循环；
4. Bitable 写操作包含串行鉴权、schema 获取、读前校验和结果验证，交互延迟较高；
5. 本地健康检查受代理环境变量影响，并会被单次 Docker 探针抖动误报；
6. Host 重启后存在数据库容器状态残留、无效 reaction 请求和未处理 dead-letter；
7. Host、Web、飞书、语音及文件监控集中在一个 Node.js 进程，日志未轮转，运行时版本也与仓库声明不一致。

本方案按 P0、P1、P2 分级实施。优先解决资源生命周期和 SMB 扫描问题，再处理事件循环阻塞、Bitable 延迟与监控误报，最后完成状态一致性、进程隔离、日志治理和运行时统一。

## 3. 优化目标

### 3.1 稳定性目标

- 正常空闲容器在 120 秒后自主退出；
- 不再因空闲退出配置缺失而触发 30 分钟绝对上限强杀；
- Docker 回收操作不再同步阻塞 Host 事件循环；
- Host 重启后数据库中不存在虚假的 `running` 或 `idle` 状态；
- 合成消息不再触发飞书 reaction 网络请求。

### 3.2 性能目标

- SMB 不可用时采用退避，不再固定每 5 秒递归扫描；
- 降低重复目录遍历、文件枚举和日志写入开销；
- Bitable 创建和删除的各阶段耗时可独立观测；
- 可批量操作使用 batch/bulk，长操作使用异步任务；
- 本地健康检查不再经过 HTTP 代理。

### 3.3 运维目标

- 使用 Node.js 22 运行服务，与 `.nvmrc` 一致；
- 日志具备轮转、限频和重复采样；
- 系统盘使用率降至安全区间，并设置容量告警；
- 将高风险文件监控逐步从组合 Host 进程中拆出；
- 对 6 条 dead-letter 完成人工分类和处置记录。

## 5. P0：容器生命周期修复

### 5.1 问题

`AGENTDESK_IDLE_EXIT_MS=120000` 没有出现在实际容器启动参数中。Runner 读取不到该配置时回退为 `0`，即关闭主动空闲退出。

结果是容器即使已经空闲，也不会在 120 秒后正常退出，而是继续存活到 30 分钟绝对上限，随后被 Host 强制停止，形成退出码 137。

### 5.2 实施方案

1. 在 `buildContainerArgs()` 中读取并校验空闲退出配置；
2. 将标准化后的值以 `AGENTDESK_IDLE_EXIT_MS` 注入实际 Docker argv；
3. 拒绝负数、非数字、超范围值，避免把错误配置传入容器；
4. 保留 Runner 对 `idleExitMs <= 0` 的关闭语义，但生产默认值必须明确注入；
5. 增加基于真实 Docker 参数数组的回归测试；
6. 修复完成后重启 Host，使新启动的容器获得配置。

### 5.3 主要实施位置

- `container/agent-runner/src/config.ts`
- `container/agent-runner/src/poll-loop.ts`
- `src/container-runner.ts`
- `src/container-runner.test.ts`
- `src/container-config.test.ts`

### 5.4 测试要求

- 默认配置生成 `AGENTDESK_IDLE_EXIT_MS=120000`；
- 自定义合法值能覆盖默认值；
- 非法值被拒绝或安全回退；
- 真实 Docker argv 中只出现一个最终值；
- 空闲 120 秒后 Runner 正常退出，退出结果归类为 idle，而不是 killed；
- 活跃任务和心跳不会被误杀。

### 5.5 验收标准

- 24 小时内不再出现因正常空闲导致的 `absolute-ceiling` 强杀；
- 正常空闲容器退出码为 0；
- 容器空闲退出时长符合配置，允许少量轮询误差；
- 容器实际环境中可以读取到 `AGENTDESK_IDLE_EXIT_MS`。

## 6. P0：SMB 扫描治理

### 6.1 问题

图片监控与 JSON 监控分别递归遍历同一个 SMB。扫描成功时频率很高，失败时仍固定每 5 秒重试。

当前数据表明：

- 已成功扫描 17,052 次；
- 平均约 3.6 秒，最慢约 603 秒；
- 单轮候选上限可达十万文件；
- 失败日志累计约 8.3 万条；
- SMB 不可用时仍持续制造 I/O 尝试和重复日志。

### 6.2 第一阶段：立即降载

1. SMB 不可用时采用指数退避；
2. 退避中加入少量抖动，避免多个扫描器同时恢复；
3. 设置最大退避时间，例如 5 分钟；
4. 对相同错误进行限频，只记录状态变化和周期性摘要；
5. 降低单轮文件候选上限；
6. 记录扫描开始、完成、跳过、失败和截断数量。

建议退避序列：

```text
5s → 10s → 20s → 40s → 80s → 160s → 300s
```

SMB 恢复后重置退避状态。

### 6.3 第二阶段：消除重复遍历

可按以下顺序选择方案：

1. 图片和 JSON 监控共享一次目录快照；
2. 使用文件修改时间、水位线或状态数据库进行增量扫描；
3. 对稳定目录维护轻量索引；
4. 如果 SMB 支持可靠事件通知，再评估事件驱动监听；
5. 将文件扫描器拆为独立进程，通过有界队列向 Host 提交结果。

独立进程是长期推荐方案，因为它能隔离 SMB 卡顿、文件系统异常和未捕获错误，不让扫描故障拖累 Web、飞书和 Host 主流程。

### 6.4 主要实施位置

- `examples/voice-photos-feishu-monitor/scanner.ts`
- `examples/voice-photos-feishu-monitor/json-scanner.ts`
- `examples/voice-photos-feishu-monitor/service.ts`
- `examples/voice-photos-feishu-monitor/json-service.ts`
- 对应 scanner/service 测试

### 6.5 验收标准

- SMB 不可用时不再每 5 秒重复递归扫描；
- 相同错误日志稳定状态下不超过每分钟一条摘要；
- 扫描最长耗时、候选数量和截断数量可观测；
- 图片和 JSON 不再对同一目录做无必要的重复完整遍历；
- SMB 超时不会导致 Host 健康端点卡住。

## 7. P1：Docker 回收路径异步化

### 7.1 问题

Host sweep 强杀容器时使用同步 `docker stop`。历史单次同步阻塞约 1.2 秒，连续回收两个容器时延迟会叠加，并阻塞 Node.js 唯一事件循环。

受影响的不只是容器管理，还包括：

- Web 请求；
- 飞书事件处理与心跳；
- 语音及文件监控；
- 健康检查；
- 定时 sweep。

### 7.2 实施方案

1. sweep 和强杀路径统一使用现有 `stopContainerAsync()`；
2. 移除主运行路径中的同步 `stopContainer()` 调用；
3. 使用有界并发回收容器，例如并发 2～4 个；
4. 为单次 stop 设置明确超时；
5. 单个容器停止失败不得阻塞其他容器清理；
6. sweep 不应串行等待所有 session 才结束；
7. 增加 stop 耗时、超时、失败和并发量指标。

### 7.3 主要实施位置

- `src/container-runtime.ts`
- `src/container-runner.ts`
- `src/host-sweep.ts`
- `src/container-runtime.test.ts`
- `src/host-sweep.test.ts`

### 7.4 验收标准

- sweep 期间 Host 事件循环不再出现约 1.2 秒的同步阻塞；
- 连续回收多个容器时 Web 和健康端点仍可响应；
- 单个 Docker stop 超时不会拖住整轮 sweep；
- 容器最终状态和 processing 状态仍能正确收敛。

## 8. P1：Bitable 延迟优化

### 8.1 问题

Bitable 是明确的业务延迟源：

- 创建平均约 1.54 秒，最大约 5.18 秒；
- 删除平均约 2.18 秒，最大约 5.89 秒；
- 写入前串行获取字段 schema；
- 更新和删除还包含读取、确认绑定及结果校验。

这些安全校验不能直接移除，但可以减少重复网络请求，并将慢操作从同步交互路径中移出。

### 8.2 实施方案

1. 延长并预热 tenant token 缓存；
2. 为字段 schema 增加有界 TTL 缓存和 single-flight；
3. 在配置加载或首个请求前预热常用资源 schema；
4. 在 schema 变化或字段校验失败时精确失效缓存；
5. 记录以下分阶段耗时：
   - auth；
   - schema；
   - pre-read；
   - write/delete；
   - verify；
6. 可合并的操作使用 batch API；
7. 可安全聚合的网关请求使用 bulk；
8. 超过交互预算的操作提交异步任务并报告进度；
9. 不削弱写前校验、确认绑定、幂等键或结果验证。

### 8.3 主要实施位置

- `examples/reference-gateway/feishu-bitable-adapter.mjs`
- `examples/reference-gateway/feishu-bitable-adapter.test.mjs`
- Bitable Gateway 的指标与审计模块

### 8.4 建议性能预算

| 操作 | 初始目标 |
| --- | ---: |
| 缓存命中的 schema 获取 | 小于 10 ms |
| 单记录创建 P95 | 小于 2.5 秒 |
| 单记录删除 P95 | 小于 3.5 秒 |
| 超过交互预算的操作 | 自动转异步任务 |

目标需要在真实网络环境中校准，不能用降低安全校验换取延迟。

### 8.5 验收标准

- 指标可以区分 auth、schema、write 和 verify 慢点；
- 并发请求不会重复刷新 token 或 schema；
- 缓存失效后能恢复到正确 schema；
- batch/bulk 不破坏原子性、确认机制和审计归属；
- 用户不再因长操作长时间看不到进度。

## 9. P1：健康检查可信度修复

### 9.1 问题

健康脚本继承 `HTTP_PROXY`，但访问 localhost 时没有使用 `--noproxy`，曾导致全部本地服务被误报失败。

此外，Host `/readyz` 会因为单次 Docker 探针抖动短暂返回 503，随后自行恢复。

### 9.2 实施方案

1. 所有访问 `127.0.0.1` 或 `localhost` 的 curl 固定增加：

```bash
--noproxy '*'
```

2. 状态检查增加 2～3 次短退避重试；
3. 区分进程存活、基础健康和依赖就绪；
4. 503 输出结构化原因，例如 Docker 不可达、数据库不可写或探针超时；
5. 不要用重试掩盖持续故障；
6. 为代理环境变量存在的场景增加脚本回归测试。

### 9.3 主要实施位置

- `examples/local-evaluation-stack/manage-services.sh`
- `src/webhook-server.ts`
- `src/webhook-server.test.ts`

### 9.4 验收标准

- 设置 `HTTP_PROXY` 和 `HTTPS_PROXY` 后，本地健康检查仍直连；
- 单次 Docker 探针抖动不会立即触发全套服务失败告警；
- 持续不可用时仍能在有限时间内返回明确失败；
- 503 响应和管理脚本均能展示失败原因。

## 10. P2：重启后的容器状态收敛

### 10.1 问题

Host 重启后存在 3 条会话长期保持 `container_status=running`，但实际处理已经完成。这些记录会被每秒投递轮询持续扫描。

### 10.2 实施方案

1. `cleanupOrphans()` 清理旧容器后，统一校正数据库中的旧 `running` 和 `idle` 状态；
2. 只有当前 Host 进程实际 spawn 并确认运行的容器才能标记为 `running`；
3. 启动时记录被修正的会话数量；
4. 增加“数据库状态与 Docker 实际状态不一致”的指标；
5. 校正操作必须幂等。

### 10.3 主要实施位置

- `src/container-runtime.ts`
- `src/db/sessions.ts`
- `src/index.ts`
- `src/host-sweep.ts`
- `src/container-runtime.test.ts`

### 10.4 验收标准

- Host 启动后旧 `running/idle` 状态归零；
- 实际启动的容器能重新正确标记为 `running`；
- 不再每秒扫描已结束的虚假运行会话；
- 重复启动和重复清理不会破坏当前活跃状态。

## 11. P2：消息 ID 与进度 reaction 修复

### 11.1 问题

合成的内部消息 ID 被当作飞书原生 `open_message_id` 添加进度 reaction，已经产生 18 次失败。该网络请求还在容器唤醒前同步等待，扩大了核心路径延迟。

### 11.2 实施方案

1. 为入站消息增加明确的 `reactable` 能力字段；
2. 区分内部合成 ID 和平台原生消息 ID；
3. 仅允许有效的飞书原生消息 ID 发起 reaction；
4. 合成消息直接跳过进度 reaction；
5. reaction 失败不得阻塞容器唤醒；
6. 可将 reaction 添加改为有界、可取消的旁路任务；
7. 保持 reaction 清理的幂等性。

### 11.3 主要实施位置

- `src/modules/progress-status/index.ts`
- `src/channels/feishu.ts`
- 入站消息类型与创建路径
- `src/modules/progress-status/index.test.ts`
- `src/delivery.test.ts`

### 11.4 验收标准

- 合成消息触发 reaction 的次数为 0；
- 原生飞书消息仍能正确添加和移除 reaction；
- reaction API 慢或失败时，容器唤醒不被同步阻塞；
- 日志能区分“不支持 reaction”和“平台 API 失败”。

## 12. P2：进程、日志与运行时治理

### 12.1 缩小组合进程故障域

当前 Host、Web、飞书、语音以及两个文件监控运行在同一个 Node.js 进程。任一模块出现未捕获异常，都可能使整套服务退出。

建议分阶段拆分：

1. 优先将 SMB 图片和 JSON 扫描器拆为独立进程；
2. 再评估语音 Bridge 与 Host 的边界；
3. Host 保留路由、会话、容器调度和核心通道职责；
4. 子服务使用独立健康检查、重启策略和日志；
5. 服务间使用有界队列或持久化交接，避免内存耦合。

### 12.2 日志治理

当前 4 天日志约 15 MB，系统盘使用率达到 91%。建议：

1. 配置按大小或按天轮转；
2. 设置保留天数和总容量上限；
3. 对 SMB 重复错误做采样和聚合；
4. 保留启动、退出、状态变化和关键错误；
5. 磁盘使用率达到 85% 时告警，达到 90% 时升级；
6. 清理旧日志前先列出精确目标并确认保留要求。

### 12.3 统一 Node.js 版本

服务当前运行 Node.js 25，但仓库 `.nvmrc` 指定 Node.js 22。

建议：

1. 服务管理脚本读取并校验 `.nvmrc`；
2. LaunchAgent 使用明确的 Node.js 22 可执行文件；
3. 启动日志记录 Node.js 主版本；
4. 版本不一致时启动失败并输出可操作原因；
5. 在 Node.js 22 下重新执行完整测试。

### 12.4 验收标准

- 文件扫描器异常不会导致 Host、Web 和飞书同时退出；
- 日志增长速度明显下降，并受容量上限控制；
- 系统盘回到安全使用区间；
- 所有生产服务使用 Node.js 22；
- 启动脚本能够检测版本漂移。

## 13. Dead-letter 处置

当前有 6 条历史入站 dead-letter。它们不是本轮卡顿的根因，但代表曾经未完成的请求。

不得自动批量重放。应逐条人工判断：

| 分类 | 处置 |
| --- | --- |
| 可安全重放的只读请求 | 在确认幂等后重放 |
| 可能产生重复写入的请求 | 先核对目标系统状态和幂等键 |
| 已由用户重新提交的请求 | 标记为无需重放 |
| 内容失效或上下文缺失 | 归档并记录原因 |
| 权限或配置问题 | 修复根因后再决定 |

处置记录应包含消息标识、失败原因分类、是否重放、操作人、时间和最终结果，但不得复制敏感消息正文到普通日志。

## 15. 发布与回滚策略

每个优化项应独立提交、独立测试，避免一次性修改所有运行路径。

建议发布流程：

1. 保存修改前基线指标；
2. 完成单项代码和回归测试；
3. 在非生产或低流量窗口验证；
4. 重启相关服务；
5. 检查 launchd、健康端点、日志和数据库状态；
6. 观察至少一个完整空闲退出周期；
7. P0 完成后观察 24 小时，再进入下一阶段。

出现以下情况应回滚单项变更：

- 活跃容器被错误退出；
- 消息出现丢失或重复处理；
- Bitable 安全校验、确认或审计被绕过；
- sweep 无法回收容器；
- 健康检查掩盖持续依赖故障；
- 新增事件循环阻塞或显著延迟回退。
